# Data Formats and Folder Structure

Everything `tghoard` generates lives inside the folder configured by `TGHOARD_DATA_DIR` / `--data-dir` (default: `./data` at the repository root).

## 1. The `<data_dir>/chats.md` Manifest

Generated by the `tghoard start` command, it lists every dialog discovered in the registered accounts:

```markdown
- [x] baixar | [ ] photos | [ ] videos | [ ] audio | [ ] files | prioridade: 5 — **Dev Brasil** (`@devbrasil`) [`supergroup_9876543210`] *(contas: conta1, conta2)*
```

- The tokens are part of the file format and stay in Portuguese: `baixar` = download this chat, `photos`/`videos`/`audio`/`files` = also download that media category, `prioridade` = priority, `*(contas: …)*` = accounts that see the chat; the section headings (`## Saved Messages`, `## Grupos e Supergrupos`, `## Canais`, `## Conversas Privadas`, `## Bots`) are kept as is too.
- The parser accepts both `[ ]` and `[]` without a space, as well as `[x]` and `[X]`.
- `prioridade: N` (integer from `-99` to `999`, default `0`): `sync` processes the highest-priority chats first. Older lines without the token count as `0`. Within each section, chats are listed by priority and then by title.
- The file can be edited by hand or through the web UI (`tghoard sync` / `tghoard web`); both write atomically, and a running `sync` re-reads the file before starting each chat. Programmatic rewrites (`start`, web UI) are serialized across processes with a lock on a hidden `.chats.md.lock` next to the file.
- **The title (`**…**`) is the only free text on the line, and it is never parsed for tokens**: checkboxes, priority, username, chat key and accounts are read from the rest of the line. When writing, line breaks/control characters and `**` are removed from titles and usernames that aren't plain Telegram usernames (`[A-Za-z0-9_]`) are dropped — so a chat whose name contains e.g. ``[ ] baixar`` or ``[`channel_1`]`` can't change any selection.
- The identifier in backticks and brackets (e.g. ``[`supergroup_9876543210`]``) is the immutable canonical key (`chat_key`).

## 2. Per-Category Layout

The archive is organized first by **content type** and then by chat. Each chat has a `<kebab-title>-<id>` folder (e.g. `dev-brasil-9876543210`; DMs use both ids, `joao-silva-5555-111`; Saved Messages, `saved-messages-<alias>-<id>`), repeated in each category:

```text
<data_dir>/
├── chats.md
├── folders.md         (each account's Telegram folders — generated, do not edit)
├── messages/
│   └── dev-brasil-9876543210/
│       ├── 2026-10-pt000.json
│       ├── 2026-11-pt000.json
│       └── 2026-11-pt001.json
├── photos/
│   └── dev-brasil-9876543210/
├── videos/
│   └── dev-brasil-9876543210/
├── audio/
│   └── dev-brasil-9876543210/
├── files/
│   └── dev-brasil-9876543210/
├── links/
│   └── dev-brasil-9876543210.md
├── metadata/
│   └── dev-brasil-9876543210/
│       ├── info.md
│       ├── members.md
│       ├── topics.md
│       ├── stories.md
│       ├── deleted_and_edits.md
│       ├── profile_history.md
│       ├── presence.md
│       └── events_and_admin_log.md
└── .tghoard/          (internal state: checkpoint.db, sessions/, avatars/, backups/, migrations.json, archive.lock)
```

- **Identity**: the first line of `metadata/<folder>/info.md` contains `` (`<chat_key>`) ``. Folders are located by this identity, not by name: a chat renamed on Telegram stays in its original folder. Two folders with the same name get a `-2`, `-3`, ... suffix.
- **Migration**: archives in the old layout (`<chat_key>__<slug>/chats/YYYY-MM-DD-ptNNN.json`) are converted with `tghoard migrate --apply` (see `cli-reference.md`).

### Chat join date

`metadata/<folder>/info.md` includes, in the accounts table, an **Entrou em** ("joined") column — when each of your accounts joined the chat (the generated archive files keep their Portuguese wording; see "Generated files" below):

- **Channels and supergroups**: the dialog's `Channel.date` (for members, it is the join date); recorded on every `sync` for all your channels, with no extra requests. Channels you have left (`left`) are ignored.
- **Basic groups**: the date and **who invited you** come from the member list of `messages.getFullChat` (the group's `date` is its creation date); obtained when the group is synced. If you created the group, the creation date is used.
- DMs, bots and Saved Messages have no join date.

### Telegram folders (`folders.md`)

On every `tghoard start`/`sync`, each account's chat folders ("Work", "Personal", shared folders…) are fetched via `messages.getDialogFilters` and written to `<data_dir>/folders.md` (machine-readable copy in `.tghoard/folders.json`):

```markdown
## Conta `alice`
### 💼 Trabalho (id 2)
- **Chats**: 3
  - **Canal Notícias** [`channel_10`] 📌
  - **Ana** [`dm_111_500`]
### 📁 Grupos (id 3)
- **Regras**: grupos
- **Chats**: 2
  ...
```

(Folder names are your own; the labels — `Conta` = account, `Regras` = rules, `grupos` = groups — are the file's fixed Portuguese wording.)

- Explicit, pinned (📌) and excluded chats are converted to `chat_key`. For rule-based folders (contacts, groups, channels, bots; except muted/read/archived) the chat list is computed from the dialogs at sync time.
- The file is always regenerated (one section per account; other accounts are preserved). A failure to fetch folders never interrupts the sync.

## 3. Message Partitioning (`messages/<folder>/YYYY-MM-ptNNN.json`)

- **Monthly grouping**: each file contains the messages of one month (`YYYY-MM`), in chronological order.
- **Uniform Naming**: All files end with `-ptNNN.json` (`3+ digits` starting at `-pt000`), **including small months that did not need to be split**.
- **Size Limit per Part**: Configured by `TGHOARD_MAX_JSON_KB` / `--max-json-kb` (default: `1024 KB` / `1 MB`). The split always happens between complete messages, keeping each file a valid, independent JSON document.

### Python Iteration Example

Thanks to the mandatory `-pt000` suffix on every file, iterating over a chat's entire history in chronological order only takes `sorted`:

```python
import json
from pathlib import Path

chats_dir = Path("data/messages/dev-brasil-9876543210")

for part_file in sorted(chats_dir.glob("*-pt*.json")):
    payload = json.loads(part_file.read_text(encoding="utf-8"))
    for msg in payload["messages"]:
        print(payload["month"], msg["id"], msg["date"], msg["sender"]["name"], msg["text"])
```

#### Media not downloaded (`downloaded: false`)

The entry keeps the metadata (`category`, `tg_type`, `tg_id`, `size_bytes`, …) without `path`, and the media waits in the `pending_media` queue of `checkpoint.db` (`tghoard verify-media` checks that it really is there; columns `attempts`, `last_error` and `retry_after` — the back-off of permanent failures). `skip_reason` says why, when there is a reason other than the category being unchecked in `chats.md`:

| `skip_reason` | Meaning | Retried |
|---|---|---|
| *(absent)* | Category not selected for this chat (`[ ] photos` …) | when you check it |
| `download_failed` | The download raised an error, the connection kept dropping, or the file arrived with a size different from the one Telegram declared (incomplete) — `pending_media.last_error` has the detail | every `sync` |
| `empty_download` | Telegram returned an empty file | every `sync` |
| `exceeds_max_media_mb` | Larger than `TGHOARD_MAX_MEDIA_MB` (no request is spent on it) | when the limit is raised |
| `missing_on_disk` / `corrupt_on_disk` | Set by `verify-media --fix`: the file was gone / had the wrong size or hash | next `sync` |

On success `skip_reason` is removed and `downloaded`, `path` and `sha256` are filled in.

#### Edits (`revisions`)

Each edit pushes the previous version into `revisions` (`revision` number, `text`, `edit_date`, `captured_at`) — the prior text is never discarded. An edit that changes only the formatting/links (e.g. the URL behind a text link) is recorded too: that revision also carries the previous `entities` and `links`.

#### Crash safety of the parts

When a month is repacked (e.g. older messages inserted at the front push messages into the next part), a part is only overwritten after every message it gives away is already on disk in its new part (with a directory `fsync` in between). An interruption can therefore leave a message in **two** parts of the same month, never in none. Readers merge such copies by `canonical_key`, and the month's next write repacks it cleanly.

## 4. Classification of the 4 Attachment Folders

| Category | Folder | Classification Rule |
| :--- | :--- | :--- |
| **`photos`** | `photos/<folder>/` | `MessageMediaPhoto` (photos from messages, Stories and profiles) and static image documents (`image/*`) without a sticker attribute |
| **`videos`** | `videos/<folder>/` | Documents with `DocumentAttributeVideo` (videos, animated MP4 GIFs, *video notes* ("round videos")) or non-sticker `video/*`, plus Story/profile videos |
| **`audio`** | `audio/<folder>/` | Documents with `DocumentAttributeAudio` (*voice notes* and music/audio tracks) or `audio/*` |
| **`files`** | `files/<folder>/` | Any other file that does not fit `photos`, `videos` or `audio` (PDFs, ZIPs, Office documents, code, `.webp`/`.tgs`/`.webm` stickers, vCards, etc.) |

## 5. `links/<folder>.md` and `metadata/<folder>/*.md`

- `links/<folder>.md`: All links extracted from raw text, formatted hyperlinks, inline buttons and Story captions, grouped by date.
- `metadata/info.md`: Chat identification, type, description/bio, statistics and the table of synced accounts.
- `metadata/members.md`: List of visible members and administrators with roles and dates.
- `metadata/topics.md`: Forum / Monoforum topics.
- `metadata/stories.md`: Catalog of Stories captured before they expired.
- `metadata/deleted_and_edits.md`: Readable chronological report of preserved deleted messages and edit history.
- `metadata/profile_history.md`: Timeline of changes to title/name, `@username`, bio and profile photos.
- `metadata/presence.md`: Snapshots of `Online` / `was_online` status and activity/typing events.
- `metadata/events_and_admin_log.md`: Service events (joins/leaves, calls with duration, pins) and events recovered from the 48h Admin Log.

## Generated files keep their Portuguese wording

The text **inside generated archive files** — `chats.md` (tokens and section headings, which are parsed), `metadata/<folder>/*.md`, `links/<folder>.md` and `folders.md` — keeps its original Portuguese labels so existing archives stay consistent and parseable (e.g. the web UI reads the `**Total de links**` line). Everything the program *prints* (CLI, logs, web UI) is in English.
